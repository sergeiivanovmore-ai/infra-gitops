# Нумерация модулей и порядковые номера пользователя

Кейс Вильены: span **134.3 × 1.05 × 2.73**, 1069 объектов. Пользователь
описывает нужные предметы **порядковыми номерами** («стол на 9, стилаж на 14»,
затем «15 с небольшим и 19 с небольшим»).

---

## Почему автоматическая нумерация не совпадает с пользовательской

Разбиение по зазорам (`gap_tol = 0.05`) дало **99 кластеров**, из которых
настоящими предметами были **77**. **22 артефакта** — детали, оторванные от
корпусов: перегородки внутри шкафов, полки в нишах, направляющие ящиков.

Показательно: кластер шириной **0.24** получил номер **19**. Пользователь
сказал «19» — и имел в виду маленький *предмет*, а не перегородку внутри
шкафа. Все последующие номера тоже сместились.

### Слияние вложенных кластеров

```python
def merge_nested(mods):
    mods = sorted(mods, key=lambda m: m["x0"])
    out = []
    for m in mods:
        merged = False
        for o in out:
            if m["x0"] >= o["x0"] - 1e-6 and m["x1"] <= o["x1"] + 1e-6:
                ow, mw = o["x1"] - o["x0"], m["x1"] - m["x0"]
                overlap = (min(o["x1"], m["x1"]) - max(o["x0"], m["x0"])) / max(ow, 1e-9)
                # ДВА признака артефакта: кратно меньше ЛИБО перекрывает >60%
                if mw < ow * 0.5 or overlap > 0.60:
                    o["x0"] = min(o["x0"], m["x0"])
                    o["x1"] = max(o["x1"], m["x1"])
                    o["n"] += m["n"]
                    merged = True
                    break
        if not merged:
            out.append(dict(m))
    return out
```

Повторять до стабилизации (5 итераций хватает) — слияние может открыть
новое вложение.

#### Порог «в 2 раза меньше» сам по себе НЕДОСТАТОЧЕН

Первая версия слияния дала правдоподобные **77 предметов**, но три из них —
**№47, №50, №68** — оказались **дубликатами №46, №49, №67** с перекрытием
**71%**. Ширина дубликата была 0.71 от родителя, поэтому условие
`mw < ow * 0.5` их не ловило. При разбиении по зазорам объекты перекрываются
по X, и кластер может быть почти такого же размера, как тот, куда вложен.

Как обнаружилось: батч отработал с `EXIT=0`, но файлов оказалось **74 вместо
77**. Три предмета получили **0 объектов** — их центры уже забрал сосед с
меньшим номером. Потери геометрии не было (`ASSIGNED=1069 of 1069`), но
номер в панораме указывал на другой предмет.

**Обязательная проверка сразу после слияния, до первого экспорта:**

```python
empty = [n for n, m in members_of_all.items() if not m]
if empty:
    raise SystemExit("предметы без объектов — незакрытые дубликаты: %s" % empty)
```

**Диагностика:** медианная ширина предмета ~1.00; у артефактов падает до
0.13–0.30. Самые узкие: №91 (0.13), №96 (0.13), №67 (0.15), **№19 (0.24)**,
№47 (0.26), №74 (0.27), №92 (0.29), №53 (0.30).

## Главный рабочий урок: не перебирать варианты

Пользователь назвал «15» и «19». Я **четыре раза подряд** строил свою
нумерацию, рендерил кандидатов и отвечал вопросом — четыре промаха,
4 полных цикла рендеров впустую.

Правильная процедура — **один** рендер, где номера уже проставлены
для пользователя:

```bash
blender --background --python scripts/render_numbered_panorama.py -- \
    --input model.fbx --out-dir /tmp/panorama --per-slice 10
```

10 кадров, на каждом 10 предметов с красным номером. Пользователь отвечает
одним числом. Дальше номера → диапазоны X переводятся программно.

**Правило: на порядковый номер отвечай картинкой с номерами, а не перебором
координат.** Это экономит и время, и доверие.

### ⚠️ Ложный вывод «счёт не с начала модели» — не делай его

По номерам 15 и 19 рендеры показали **низкие подвесные тумбы** (4 ящика
и 1 ящик), а пользователь описывал **стол** и **стеллаж**. Я сделал вывод:
«нумерация всё равно не та, значит счёт ведётся не с начала модели» — и
потратил на этот вывод ещё цикл рендеров.

**Вывод был ложным, потому что номера 15/19 были взяты из нумерации ДО
слияния.** В нумерации **после** слияния те же координаты — это другие
предметы.

Проверка после слияния (свелась с первого раза):

| № (после слияния) | X | Ширина | Что на рендере | Совпало с описанием? |
|---|---|--------|----------------|----------------------|
| **7** | 13.62–14.92 | 1.30 | **стол**: тумба с **2 ящиками** (овальные вырезы-ручки) + открытое подножие справа | ✅ «стол с закрытыми ящиками» |
| **11** | 19.25–19.75 | 0.50 | **стеллаж**: **4 открытые полки** + **2 ящика** внизу, h 2.20 | ✅ «стилаж» |

Пользователь ответил «7 и 11 элементы» — и это были ровно те предметы.

**Правило, которое важнее всех остальных здесь:**

> **Слияние вложенных модулей — это не «улучшение нумерации», а условие её
> корректности. Сделай его ДО первого рендера-кандидата.**
> Показывать номера из сырой кластеризации и подбирать предмет рендерами —
> гарантированный промах: 22 из 99 номеров указывают на перегородки внутри
> шкафов, поэтому «15» из сырого списка и «15» после слияния — **разные
> предметы**, а разницу не видно ни в цифрах, ни в таблице координат.

Порядок, который сработал за один ответ пользователя:

```
probe (границы объектов → JSON)   → числа, не догадки
merge_nested (99 → 77)            → визуальная нумерация
render_numbered_panorama          → номера на картинке
пользователь: «7 и 11»            → один ответ
номер → X программно               → без перебора
рендер + vision_analyze           → сверка типа мебели
экспорт FBX + рендер + Drive
```

### Сверка рендера с описанием — обязательна, но это проверка, а не диагноз

Сверяй рендер с описанием пользователя (стол/стеллаж/ящики) **до** выгрузки
на Drive. Но если не сошлось — **сначала проверь, из какой нумерации взят
номер** (сырая или слитая), и только потом спрашивай пользователя про сдвиг
счёта. Порядок «спросить про сдвиг» без этой проверки = ещё один цикл впустую.

Рабочая диагностика при расхождении:

1. номер взят из сырой кластеризации? → слить и пересчитать, **не спрашивать**
2. предмет по этому номеру физически другой тип (высокий корпус вместо стола)?
   → сверить с `height_profile.py`, вдруг диапазон не тот
3. только после 1–2 — задать пользователю один уточняющий вопрос

## Технические грабли Blender (воспроизведены и исправлены)

### 1. `RuntimeError: No active camera`

`bpy.ops.view3d.camera_to_view_selected()` в `--background` требует
активной камеры **сцены**, а не только активного объекта:

```python
sc.camera = cam                                  # обязательно
area.spaces.active.camera = cam                  # обязательно
with bpy.context.temp_override(window=win, area=area, region=reg,
                               space_data=sp, scene=sc,
                               view_layer=bpy.context.view_layer):
    bpy.ops.view3d.camera_to_view_selected()
```

Без этого скрипт падает, и PNG не создаётся вовсе — выглядит как «рендер
прошёл, но файла нет».

### 2. Своя формула кадра ломается на вытянутых моделях

Самописный расчёт расстояния дал **6906** при bbox 14×1×2 — объект
превратился в точку. **Не пиши формулу кадра руками**, используй
`camera_to_view_selected()`.

### 3. `TypeError: '<' not supported between instances of 'Object'`

```python
sorted(meshes, key=lambda o: (sx(o), ex(o)))   # ОК
sorted((sx(o), ex(o), o) for o in meshes)      # падает при равных координатах
```

`bpy.types.Object` не поддерживает сравнение. Сортируй по координате,
объекты не клади в кортежи.

### 4. Кириллица: блокировка терминала И подмена омоглифов

**4a. Терминал отклоняет путь.** `workdir` с кириллицей
(`/opt/data/workspace/dsh_model_split/Вильена`) не проходит. ASCII-симлинк:

```bash
ln -sfn "/opt/data/workspace/dsh_model_split/Вильена" /tmp/vil
# дальше работать через /tmp/vil
```

**4b. Омоглиф внутри скрипта — тише и опаснее.** При записи python-файла
кириллическая **«е»** превратилась в латинскую `e`: путь стал
`.../Вильena`, `os.path.isdir()` вернул `False`, и скрипт молча показывал
**0 файлов** при реальном наличии на диске. Никакой ошибки — просто
неверные счётчики.

```python
# ПЛОХО: хардкод кириллицы в скрипте
D = "/opt/data/workspace/dsh_model_split/Вильена"

# ХОРОШО: путь находится через glob, омоглиф невозможен
D = glob.glob("/opt/data/workspace/dsh_model_split/*иль*")[0]
```

**Проверяй `os.path.isdir(D)` первой строкой** любого скрипта с длинным
путём — иначе ошибка проявится через «0 файлов», а не через исключение.

### 5. Тёмный/выжженный кадр

При копировании скрипта легко потерять блок света и мира — кадр выходит
почти чёрным. Задавай явно: `SUN 3.2`, `AREA 400`, `world (0.95,0.96,0.98)
strength 1.2`, `view_transform='Standard'`.

### 6. Один импорт на много кадров

1069 объектов; повторный импорт в каждом кадре — минуты впустую. Импортируй
**один раз** и переключай `o.hide_render` по диапазону X.

## Probe сначала: координаты из данных, а не из картинки

Прежде чем рендерить хоть один кандидат, выгрузи границы объектов в JSON.
Один импорт FBX — секунды, и дальше вся работа идёт по числам:

```bash
# вся модель → объекты + кластеры по зазорам, в JSON
python3 .../scripts/probe_bounds.py \
    --input model.fbx --out all_modules.json --x0 -1e9 --x1 1e9 --gap-tol 0.05
# либо зона: --x0 13.0 --x1 22.5
```

На выходе — `objects[]` (имя, min, max, центр, высота, число вершин) и
`groups[]` (границы кластеров, число объектов). Дальше слияние, нумерация и
перевод номера в диапазон X — обычный питон по этому файлу, без Blender.

**Почему это важно:** попытка назвать координаты «по рендеру» провалилась
четыре раза подряд. Рендер показывает *вид*, но не границы. Числа из probe
не врут — на Вильене диапазон 13.60–14.94 сразу дал предмет шириной ровно
1.30 и 11 объектов, и это совпало с описанием пользователя с первой попытки.

Побочная польза: probe даёт и **готовый `items_index.json`** — сохрани его
рядом с моделью, чтобы нумерацию не пересчитывать в следующей сессии
(см. `references/pre_drive_verification.md`).
