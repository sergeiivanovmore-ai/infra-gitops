# Интерактивный сценарий: Drive-папка → выбор файлов → выбор частей → результат

Полное пошаговое описание диалога с пользователем.

**Ключевой принцип: сначала имена файлов (без скачиваний), потом вопрос,
потом анализ только выбранного.** Никогда не начинай массовую работу до
выбора пользователя.

> **Это ветка с числовым выбором** (прогноз → «сколько частей» → «какие номера»).
> Если модель — плотный модульный ряд без зазоров, или пользователь просит
> «отрендери и пришли, я выберу» — иди в `visual_selection_workflow.md`:
> там другой порядок и другие инструменты (`--ticks`, срезы, склейка).
> Порядковые номера вида «7-я слева» там **не угадываются**, а переводятся
> в координаты через `--ticks`.

---

## ⚠️ Обязательные точки подтверждения

Пайплайн интерактивный: пользователь сам решает, что обрабатывать и какие
части оставить. Есть **две жёсткие точки остановки**:

| Точка | Показываешь | Спрашиваешь | Пока не ответил |
|-------|-------------|-------------|-----------------|
| **Шаг 2** | список имён + размеры (`list_files.py`) | «какие файлы обрабатывать?» | **ничего не качай, не запускай Blender** |
| **Шаг 4** | прогноз числа частей по каждому выбранному | «сколько частей сохранить?» | **не запускай split/render/upload** |

Не объединяй точки в один вопрос: пользователь может обработать файлы 1 и 3,
но из первого оставить части 1–3, а из третьего — только 1. Прогноз показывай
**по каждому файлу отдельно**.

Не задавай вопросов, на которые ответ уже есть: если модель не названа —
возьми её из конфига; если пользователь сразу сказал «все FBX» — не
переспрашивай про файлы, но всё равно покажи имена и дождись подтверждения.

## Шаг 1. Пользователь даёт ссылку

Типичные фразы:
- «раздели модели из этой папки: https://drive.google.com/drive/folders/1AGz…»
- «возьми FBX из Veresk»
- «разбери все модели в 3dmodels»

Опционально сразу может задать:
- число частей (`--parts`). **Если не задал — не придумывай: считай `auto`**
- модель для агента (если не задана — берём из `/opt/data/config.yaml`:
  `model.provider` + `model.default`)

**Если модель не указана — используй модель из конфига Hermes.** Не переспрашивай.

## Шаг 2. Показать имена файлов — БЕЗ скачивания

```bash
python3 .../scripts/list_files.py --folder "<ссылка>"
```

~0.3 сек: только метаданные Drive, **ничего не скачивается, Blender не
запускается**. Выводит `LIST_JSON {...}` и готовый блок для показа.

Формат ответа пользователю:

```
В папке 3 FBX-файла:

1. Penaly.FBX                    — 15.2 МБ
2. Вильена.fbx                   — 75.4 МБ
3. Спейс прямой,  угл 1, 2.fbx  — 19.2 МБ

Какие обрабатывать? (номера, например «1 и 3», или «все»)
```

**Жди ответа пользователя.** Не запускай прогноз и не качай ничего.

> ⚠️ **Почему нельзя сразу прогнать прогноз по всей папке.** В реальной папке
> это сотни мегабайт и минуты анализа ради чисел, которые пользователь может
> и не выбрать. Реальный пример: папка из 3 файлов (15 + 75 + 19 МБ,
> 1069 объектов в «Вильена») дала прогноз **181 часть** — рендерить её
> пользователь бы не стал.

## Шаг 3. Прогноз по ВЫБРАННЫМ файлам

Только теперь скачиваются и анализируются выбранные файлы:

```bash
python3 .../scripts/predict_batch.py \
    --folder "<ссылка>" \
    --files "id1,id2"          # ОБЯЗАТЕЛЬНО после выбора пользователя
```

**Не передавай `--parts`** — тогда работает `auto` и число частей считается
по естественным зазорам: N = зазоры + 1.

Альтернативные вызовы:
```bash
--parts 6          # ровно 6 частей (топ-5 зазоров)
--robust           # считать только крупные зазоры (>1% длины модели)
--force            # сбросить кэш прогноза
```

Скрипт:
1. Разрешает ссылку в ID папки (`gdrive_ops.resolve_folder_id`)
2. Скачивает **только выбранные** файлы в `<workdir>/<имя>/input/`
3. Запускает `predict_parts.py` в Blender — определяет ось, зазоры, число частей
4. Печатает `BATCH_JSON` с результатами

Результат кэшируется в `<workdir>/_predict_cache.json` по ключу
`file_id|parts|axis|robust`. Повторный вызов с теми же параметрами не качает
и не считает заново.

> 🛡 **Защита:** без `--files` при >1 файле скрипт **откажется работать**
> (код возврата 2) и вернёт список имён с напоминанием. Так нельзя случайно
> скачать всю папку.

## Шаг 4. Сообщить прогноз и спросить число частей

Из `BATCH_JSON`. **Показывай обе цифры — по всем зазорам и по крупным:**

```
1. Penaly.FBX — ось X, 110 объектов
   по всем зазорам:  10 моделей
   по крупным (>1%):  6 моделей

3. Спейс прямой,  угл 1, 2.fbx — ось X, 63 объекта
   по всем зазорам:   5 моделей
   по крупным (>1%):  3 модели
```

**Важные пометки (поле `warnings`):**
- `gaps_robust < gaps_usable` → часть зазоров — щели между мелкими деталями.
  Обязательно покажи обе цифры и дай выбор.
- `planned_parts > 20` → предупреждение о времени рендера, предложи `--robust`
  или фиксированное число.
- `not_enough_gaps: true` → запрошено больше частей, чем есть зазоров.

**Обязательно выводи `gaps_top[0].gap_pct` отдельной строкой** и сравни с
`gaps_top[1]`: если первый ≥3–4× второго, это **доминирующий зазор** —
вероятная граница между изделиями. Тогда предложи и этот вариант
(обычно 2 части), а не только дилемму auto-против-числа.

Детализация по частям (если нужна):
```
   1 — 17 обь, диапазон -1.34 … -0.84
   2 —  2 обь, диапазон -0.73 … -0.72
   ...
```

Вопрос (можно совместить с выбором номеров):

```
Какое число частей использовать — 10 (все зазоры) или 6 (крупные)?
И какие части выгружать — все или конкретные номера?
```

Ответ вида «6, все» → `--parts 6 --select all`.
Ответ вида «6, только 1,3,5» → `--parts 6 --select 1,3,5`.
Можно указать разные наборы: «Шкаф: 1,2,3; Стеллаж: 1,2».

**Жди ответа.** Число передаётся в `--parts`, номера — в `--select`.

## Шаг 5. Обработка — последовательно, файл за файлом

```bash
python3 .../scripts/process_file.py \
    --folder "<ссылка>" --file-id ID --file-name "Шкаф.fbx" \
    --parts 6 --select "1,3"      # 6 — число, выбранное пользователем
```

Скрипт печатает построчный JSON. **Отправляй пользователю статусы по мере
поступления:**

```json
{"stage":"start","status":"begin","file":"Шкаф.fbx"}
{"stage":"download","status":"start"}          → «Скачиваю Шкаф.fbx…»
{"stage":"download","status":"done","size_mb":24.1}
{"stage":"predict","status":"done","planned_parts":6,"parts_mode":"fixed","axis":"X"}
{"stage":"predict","status":"warning","detail":"Из 9 зазоров только 5 крупных..."}
{"stage":"select","status":"done","selected":["1","3"]}
{"stage":"split","status":"start"}             → «Разбиваю на части 1 и 3…»
{"stage":"split","status":"done","exported":["1","3"]}
{"stage":"render","status":"start"}            → «Рендерю изометрию…»
{"stage":"render","status":"item","part":"1","ok":true}
{"stage":"render","status":"item","part":"3","ok":true}
{"stage":"render","status":"done","count":2}
{"stage":"upload","status":"start"}
{"stage":"upload","status":"folders","root":"https://…"}
{"stage":"upload","status":"item","kind":"models","name":"1.fbx","id":"…"}
{"stage":"upload","status":"item","kind":"renders","name":"1_iso.png","id":"…"}
{"stage":"upload","status":"done","counts":{"models":2,"renders":2}}
{"stage":"done","status":"ok","folder_url":"https://drive.google.com/drive/folders/…"}
```

**Порядок внутри одного файла:** download → predict → split → render → upload.
Файл целиком, затем следующий. Если файлов несколько и рендер долгий —
запусти `process_file.py` для всех в фоне (`background=true,
notify_on_complete=true`) и отправляй статусы по логу.

> 🛡 **Защита:** если забыть `--parts`, скрипт скачает файл, посчитает прогноз,
> напечатает `{"stage":"await_choice","status":"paused",...}` и **остановится**
> с кодом возврата 3. Ничего не разделяет и не загружает.

## Шаг 6. Проверить рендеры глазами — до финального отчёта

Прогон `vision_analyze` по каждому `renders/*_iso.png`.

Что искать:
- **Обрезание модели** — симптом неверного target камеры
- **Дублированные объекты** — симптом провала изоляции сцены
- **Части из 2–4 объектов при ширине в разы меньше соседей** — мусорный класс
  из щели, а не элемент мебели. Переразбить с `--robust`
- **Что это вообще за мебель** — bbox может врать (см. `worked_example.md`:
  span 9.4×1.6×0.8 выглядел как шкаф, оказался диваном)
- **Оторванные панели/дверцы** — сначала отрендери оригинал и сравни: двери
  бывают открыты в исходнике. Если они отделены и там — это не дефект сплита,
  а признак слишком мелкого разбиения

```bash
# сравнение с оригиналом: --select ждёт имя БЕЗ расширения
blender --background --python render_parts.py -- \
    --models-dir <workdir>/<Имя>/input --out-dir /tmp/orig \
    --select "<Имя_без_расширения>" --samples 16 --res 512
```

Если нашлось расхождение — сообщи пользователю и предложи переразбить,
не выдавай результат за готовый.

> 💡 **Пользователь ждёт ответа, а не отчёта.** Если после просмотра рендеров
> видно, что разбиение лучше сделать иначе, **скажи об этом сразу и предложи
> вариант**, даже если файлы уже загружены. Перезагрузка дешевле и честнее,
> чем ждать, пока пользователь сам заметит. Старую папку удали через
> `gdrive_ops.delete_file(root_id)`, чтобы не осталось дублей на Drive.

> 🎯 **Проверь доминирующий зазор.** Сравни `gaps_top[0].gap_pct` со
> `gaps_top[1].gap_pct`: если первое ≥3–4× второго, этот зазор — вероятная
> граница между изделиями, и резать ниже него не стоит. Кейс Penaly — в
> `references/worked_example.md`.

## Частые ситуации

### Пользователь не указал число частей
**Не подставляй 4 и не придумывай число.** Считай прогноз в режиме `auto`
и покажи обе цифры — спроси, какое взять. Это осознанное решение пользователя:
число частей определяется геометрией модели, а не константой в пайплайне.

### Число частей уже выбрано пользователем
Передай зафиксированное число явно: `--parts 6`. Прогноз всё равно выполняется
внутри `process_file.py` и используется для нумерации частей.

### Мягкая мебель (диван, кресло)
Подушки, валики и подлокотники лежат свободно и создают щели <1% длины модели.
В режиме `auto` это завышает число частей. Показывай `planned_parts_robust`
первым и объясняй, почему часть с 4 объектами — это щель, а не секция:
сравни количество объектов и ширину с соседями.

### Прогноз дал очень много частей (100+)
Скорее всего модель составная (1069 объектов). Покажи `planned_parts_robust`,
предложи `--min-gap-ratio 0.01` или фиксированное число. Не начинай рендер
такого количества без явного согласия.

### Пользователь указал модель
Передай её в DSH-вызов, если используешь DSH:
```
provider = <указанный пользователем>
model    = <указанный пользователем>
```
Иначе — из `/opt/data/config.yaml` (`model.provider`, `model.default`).

### `not_enough_gaps: true`
Запрошено фиксированное число частей, а зазоров хватает на меньшее.
Сообщи пользователю фактическое число (`planned_parts`) и предложи его как
основной вариант. Если он настаивает на своём числе — разбиение всё равно
сработает, просто части получатся неравномерными.

Направление регулировки: `min-gap-ratio` **больше** → мелких зазоров отсекается
больше → частей меньше. Ноль (дефолт) — учитывается любой положительный зазор.

### Модель в Drive повреждена
Если скачался файл < 1 КБ или Blender не находит мешей — сообщи пользователю,
попроси перезалить. Скрипты проверяют `size == 0`, но не валидность FBX.

### Повторный запуск того же файла
Папки переиспользуются (`find_or_create_folder`), локальные файлы перезаписываются.
Для Drive-файлов используются те же имена — **Drive создаст дубликаты**.
Если нужно без дублей — удалить старую папку: `gdrive_ops.delete_file(root_id)`.
