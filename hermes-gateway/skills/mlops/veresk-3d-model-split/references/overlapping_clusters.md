# Перекрывающиеся кластеры: разбиение по центрам вместо зазоров

Кейс **Дарио** (2026-10-03): 2375 объектов, размах 326.5 по X, габариты 326.5 × 1.08 × 2.64.

Вильена и Дарио — один класс задачи (плотный модульный ряд), но ведут себя
по-разному, и разница ломает стандартный алгоритм.

---

## Симптом: зазоры есть, а части выходят пересекающимися

Первое, что бросается в глаза при сравнении:

| | Вильена | Дарио |
|---|---|---|
| объектов | 1069 | 2375 |
| размах по X | 134.3 | **326.5** |
| сумма ширин объектов | ~119.8 | **2063.3** |
| отношение сумма/размах | 0.9× | **6.3×** |

**Отношение больше единицы означает перекрытие объектов вдоль оси.** У Дарио
объекты в сумме занимают в 6 раз больше длины, чем длина самого ряда.

Причина — распахнутые двери и выдвинутые ящики: створка физически заходит в
X-диапазон соседнего модуля. У Вильены отношение 0.9× — двери закрыты,
перекрытия нет.

### Что даёт кластеризация по зазорам bbox на перекрытой модели

```python
order = sorted(meshes, key=lambda o: (sx(o), ex(o)))   # по левому краю
# режем, когда левый край следующего отстоит от правого края предыдущего
if sx(p) - ex(cur[-2]) > gap_tol:
    ...
```

Сортировка по **левому краю** при перекрытии бессмысленна: у группы А `x1`
может быть больше, чем `x0` группы Б. Получившиеся группы **перекрываются**:

```
№1  X 15.94 – 16.44
№2  X 16.08 – 17.43      ← перекрытие с №1
```

При экспорте «выбрать объекты, попавшие в диапазон» такой предмет попадёт
в две части одновременно → **дублирование геометрии**. Проверка суммы
объектов это поймает: 2637 «объектов» при 2375 реальных.

### Решение: кластеризация по координате центров

```python
order = sorted(meshes, key=lambda o: (sx(o) + ex(o)) / 2.0)
raw, cur = [], [order[0]]
for p in order[1:]:
    cur.append(p)
    if ctr(p) - ctr(cur[-2]) > thr:
        raw.append(cur); cur = [p]
raw.append(cur)
```

Сортировка по возрастанию **центра** гарантирует, что группы идут строго по
порядку и не пересекаются: у любого объекта группы i центр меньше центра
любого объекта группы i+1. Каждый объект попадает ровно в одну часть,
сумма объектов по частям равна числу объектов модели — это и есть проверка.

В `render_numbered_panorama.py` это `--method center` (по умолчанию остаётся
`gap` — для разнесённых модулей он точнее и не трогает существующее поведение).

## Подбор порога: таблица, а не догадка

Порог **0.5** выбрал наугад и это стоило полного прогона впустую: при 1.5
получилось 39 предметов, но №1 **раздулся до 130 единиц и 868 объектов** —
между X 15.9 и 145.9 нет разрыва между центрами больше 1.5, объекты смыкаются
непрерывной цепью. Кадр с таким гигантом нечитаем: мебель превращается в
диагональную полоску.

Правильный ход — **посчитать все пороги и посмотреть на распределение ширин**:

```python
objs = sorted(objects, key=lambda o: o["ctr"])
for thr in (0.3, 0.4, 0.5, 0.6, 0.8, 1.0, 1.5):
    gs = groups_at(thr)
    ws = sorted(g[-1]["max"] - g[0]["min"] for g in gs)   # ширина каждой части
    giants = sum(1 for w in ws if w > 8)                  # «гиганты» > 8 единиц
    print(thr, len(gs), "max=%.2f" % ws[-1], "median=%.2f" % ws[len(ws)//2], giants)
```

Результат по Дарио:

| порог | предметов | макс. ширина | медиана | гигантов >8 |
|-------|-----------|--------------|---------|--------------|
| 0.3 | 347 | 2.98 | 0.50 | 0 |
| 0.4 | 310 | 3.00 | 0.50 | 0 |
| **0.5** | **211** | **6.11** | **1.01** | **0** |
| 0.6 | 172 | 14.30 | 1.36 | 1 |
| 0.8 | 128 | 17.85 | 1.50 | 1 |
| 1.0 | 77 | 37.47 | 1.60 | 7 |
| 1.5 | 39 | 129.99 | 1.76 | 8 |

**Выбор: порог без единого «гиганта».** Для Дарио это 0.5 → 211 предметов.

Считать гиганты нужно **всегда** перед рендером. Один кластер шире 8 единиц
при длине ряда 326 — это уже не предмет мебели, а ошибка кластеризации,
и она сразу ломает кадрирование панорамы.

Ориентир «8 единиц» = примерно 2–3 корпуса стандартного шкафа. Для очень мелкой
мебели порог стоит снизить, для крупных модулей — поднять; мерить всегда по
своей модели.

### Почему гигант возникает

Цепочка объектов, у которой соседние центры расходятся меньше порога,
неразрывается до самого конца. В Дарио это цепочка из 868 объектов на 130
единиц — то есть между соседними элементами нет даже 1.5 единицы свободного
пространства ни по центру.

Если в вашей модели порог «без гигантов» даёт слишком мелкое разбиение
(например 300+ предметов при медиане 0.5), это сигнал, что ряд действительно
плотный и лучше резать крупнее: **покажите пользователю панораму и спросите**,
а не навязывайте число.

### Обратная сторона мелкого порога: 37 «предметов» — это не мебель

Порог 0.5 дал ровную структуру без гигантов, но **37 из 211** предметов
оказались мусором: ширина < 0.3 при высоте до 2.5.

| ширина | предметов | что это |
|--------|-----------|---------|
| 0.019 | 12 | обломок / край панели |
| 0.044 | 4 | то же |
| 0.064 | 9 | ножка, цоколь |
| 0.265 | 12 | доборная стойка между корпусами |

Видно это прямо на рендере: на кадре **61–70** предметы 61, 63 и 67 —
тонкая стойка и два обломка, а 62, 64–66, 68–70 — настоящие корпусные шкафы.

**Почему `merge_nested` их не съел.** Он требует вложенности
(`m.x0 >= o.x0 and m.x1 <= o.x1`). Стойка **между** двумя корпусами —
отдельный кластер в X-зазоре, а не вложенный обломок. Условие принципиально
не срабатывает, сколько итераций ни повторяй.

**Что делать:** диагностировать по ширине **до** рендера (дёшево, секунды),
и назвать пользователю диапазоны номеров — не выдавать их за модули:

```python
thin = [i for i in items if i["width"] < 0.3]     # порог = ~1/3 медианы (1.01)
print("узких: %d из %d" % (len(thin), len(items)))
```

Тонкий предмет — это **не повод пересобирать панораму**: он честно виден
и пронумерован, пользователь сам решит, сливать его с соседями или оставить
как доборный элемент.

## Кадрирование панорамы: пять обязательных вещей

Проверено на Дарио. Первые два пункта давали нечитаемый результат, третий —
результат, который выглядит правильным, а на деле обрезан.

### 1. Метки должны быть развёрнуты к камере

Объект `FONT` по умолчанию лежит в плоскости XY — **плашмя**. При изометрии
цифры видны с сильным сокращением и не читаются:

```python
VIEW = Vector((0.55, -0.62, 0.42)).normalized()
LABEL_ROT = VIEW.to_track_quat('Z', 'Y').to_matrix()
ob.rotation_euler = LABEL_ROT.to_euler()      # цифра лицом к зрителю
```

Тот же `VIEW` использовать для позиционирования камеры — тогда направление
нельзя случайно развести с поворотом меток.

Плюс **чередование высоты**: предметы стоят плотно, и метки на одной высоте
сливаются (на Дарио «107» и «108» печатались поверх друг друга):

```python
tier = (i - 1) % 2
ob.location.z = zt + PAD + tier * LABEL_SIZE * 2.1
```

### 2. Не использовать `camera_to_view_selected` — считать кадр аналитически

Оператор подбирает дистанцию по габаритам, но у него **две проблемы**:

- в `--background` у Blender может не быть 3D-окна, и оператор **не выполнится
  вовсе** — скрипт отрендерит с исходной дистанцией;
- он **не учитывает перспективное расширение по глубине**: в изометрии ряд
  предметов идёт по диагонали, и ближний конец выходит за нижний край.
  На Дарио правый край обрезал шкаф №10.

Отодвинуть камеру на фиксированный коэффициент (`--margin 1.14`) — это
**подпорка вслепую**: она гарантирует пустое поле, но не вписывание. Правильно —
считать кадр самому:

```python
ASPECT = res_x / float(res_y)
TAN_X  = (cd.sensor_width / 2.0) / cd.lens
TAN_Y  = TAN_X / ASPECT          # ← ДЕЛИТЬ. Не умножать (см. п.3)

def fit_camera(pts, fill=0.90, iters=80):
    """Дистанция + смещение цели так, чтобы pts легли в кадр."""
    d = max((p - tgt.location).length for p in pts) * 3.0
    for _ in range(iters):
        cam.location = tgt.location + VIEW * d
        bpy.context.view_layer.update()
        M = cam.matrix_world.inverted()
        us, vs, ds = [], [], []
        for p in pts:
            q = M @ p; z = -q.z
            us.append((q.x / (z * TAN_X)) * 0.5 + 0.5)
            vs.append((q.y / (z * TAN_Y)) * 0.5 + 0.5)
            ds.append(z)
        u0, u1, v0, v1 = min(us), max(us), min(vs), max(vs)
        du = (u0 + u1) / 2 - 0.5          # увести содержимое в центр кадра
        dv = (v0 + v1) / 2 - 0.5
        s  = max(u1 - u0, v1 - v0) / fill  # >1 → не влезает, отходим
        if abs(s - 1) < 0.002 and abs(du) < 0.002 and abs(dv) < 0.002:
            break
        zref = sum(ds) / len(ds)
        r3 = cam.matrix_world.to_3x3()
        tgt.location = (tgt.location
                        + (r3 @ Vector((1, 0, 0))) * (du * 2 * zref * TAN_X)
                        + (r3 @ Vector((0, 1, 0))) * (dv * 2 * zref * TAN_Y))
        d *= s
    return (u0, u1, v0, v1)
```

`pts` — углы bbox всех видимых мешей **и** меток слайса. Обязательно печатать
результат: `worst_margin ≈ 0.05` означает, что содержимое вписалось с полями.

### 3. Вертикальный FOV — считать правильно, иначе дефект невидим

При `sensor_fit='AUTO'` и `res_x > res_y` `sensor_width` отображается на
**ширину** кадра. Значит:

```
полуширина = z * TAN_X
полувысота = z * TAN_X / ASPECT      ← ДЕЛИТЬ на ASPECT
```

Ошибка `z * TAN_X * ASPECT` завышает вертикальный обзор в ASPECT раз — при
2600×760 это **в 3.4 раза**. Она коварна: **по горизонтали кадр выглядит
идеально** (`u[0.050..0.950]` — ровно под `fill`), а по вертикали содержимое
вылезает за оба края. Числа в логе показывают «правильный» результат, поэтому
дефект ловится только глазами на рендере.

Делить на ASPECT нужно в **трёх** местах: проекция `v`, сдвиг цели по вертикали,
пересчёт при смене пропорций кадра.

### 4. Пропорции кадра — под содержимое, а не фиксированные

Диагональный ряд в изометрии не совпадает по пропорциям с кадром 2600×760:
после правильного кадрирования вертикаль исчерпана (`v[0.05..0.95]`), а ширина
занята на **59%** — по бокам пустые поля, предметы мелкие.

Подбирать высоту кадра под содержимое каждого слайса и перекадрировать:

```python
eu = max(u1 - u0, 1e-6); ev = max(v1 - v0, 1e-6)
want_y = int(round(res_x * ev / eu))          # заполнить ширину
want_y = max(min_res_y, min(max_res_y, want_y))
set_aspect(want_y)                            # меняет TAN_Y → перекадрировать
u0, u1, v0, v1 = fit_camera(pts)
```

Ограничители обязательны: без них одиночный предмет даст кадр высотой в
тысячи пикселей.

### 5. Проверять один кадр перед полным прогоном

`--only-slices 1,11,22` рендерит три кадра (первый, средний, последний) — дёшево,
~1 минута, и экономит полный прогон на 22 кадра. Проверять надо **первый,
средний и последний**: дефекты кадрирования проявляются на краях диагонали,
а последний кадр часто содержит один предмет и крайние пропорции.

Порядок: подобрал порог по таблице → `--only-slices 1,11,22` → посмотрел глазами →
запустил все кадры.

Размер кадра под длину ряда: при `--per-slice 10` и пороге 0.5 один кадр
занимает ~14 единиц, высота мебели 2.6 — это читаемо. Для `--per-slice 5`
и порога 1.5 (гигант 130 единиц) кадр нечитаем.

## Проверка перед «готово» на перекрытых моделях

Две проверки, обе ловят именно перекрытие:

1. **Сумма объектов по частям == числу объектов модели.** При дублировании
   сумма больше (2637 против 2375). Скрипт разделения печатает
   `ASSIGNED=<n> of <total> meshes` и список `MISSING` — обе строки обязательны.
2. **Повторный импорт всех частей в одном запуске Blender** и сверка суммы
   объектов (`scripts/verify_all_parts.py`). Один запуск на весь комплект,
   а не по запуску на файл.

Пересекающиеся диапазоны при этом видно сразу — части нумерации идут
не монотонно, если не сортировать по центрам.

## Сводка

| решение | почему |
|----------|--------|
| сумма ширин / размах > 1.5 | объекты перекрыты → метод `gap` даст пересекающиеся части |
| `--method center` | гарантирует непересекающиеся части, сумма объектов сходится |
| порог по таблице, критерий «нет гигантов» | один кластер шире 8 единиц ломает и кадрирование, и смысл |
| тонкие предметы (ширина < 1/3 медианы) — назвать пользователю | `merge_nested` ловит только вложенные; стойка между корпусами остаётся отдельным номером |
| метки лицом к камере + чередование высоты | иначе цифры плашмя; на одной высоте сливаются |
| кадр считать аналитически, не `camera_to_view_selected` | в `--background` оператор может не выполниться, а перспективное расширение по глубине не учитывает — край обрезан |
| `TAN_Y = TAN_X / ASPECT` (делить) | умножение завышает вертикальный обзор в 3.4×, и дефект виден только глазами: лог показывает идеальный `u[0.05..0.95]` |
| `--auto-aspect 1` | диагональный ряд не вписывается в фиксированные пропорции — по бокам пустые поля, предметы мелкие |
| `--only-slices 1,11,22` перед прогоном | экономит полный перерендер при плохом кадре; проверять первый, средний и последний |
