# Долгие батчи: отчёт о прогрессе без спама

Прогон 77 предметов (разделение + рендер 128 spp) идёт **~80 сек на предмет** —
около двух часов. Пользователь попросил отчёт **каждые 5 минут**. Наивный
cron с агентом на каждый тик означает 24 холостых вызова LLM; правильный
режим — `no_agent` + скрипт, который **молчит, если прогресса нет**.

## Почему `no_agent=True`

При `no_agent=False` планировщик поднимает агента на каждый тик и в контекст
идёт вся схема инструментов (~22 тыс. токенов). Здесь ответ — одна строка
чисел, агент не нужен.

Ключевое правило доставки:

| stdout скрипта | Что происходит |
|----------------|---------------|
| непустой | сообщение уходит пользователю **дословно** |
| пустой | **тишина**, ничего не отправляется |

Пустой stdout — это не сбой, а штатное «никчего не изменилось».

## Скрипт-отчёт: считаем состояние, молчим без изменений

```python
#!/usr/bin/env python3
"""Пустой stdout = молчание."""
import os, json, re, glob

LOG = "/tmp/vil/split77.log"
STATE = "/tmp/vil/progress_state.json"
# NB: кириллица в пути ломается омоглифами — ищем папку через glob
_c = glob.glob("/opt/data/workspace/dsh_model_split/*иль*")
D = _c[0] if _c else "/opt/data/workspace/dsh_model_split/"
TOTAL = 77

done = 0
last_n = None
if os.path.exists(LOG):
    with open(LOG, errors="ignore") as f:
        for line in f:
            m = re.match(r"^ITEM (\d+)/(\d+) n=(\d+) objects=(\d+)", line)
            if m:
                done += 1
                last_n = int(m.group(3))

n_models = len(os.listdir(D + "/models")) if os.path.isdir(D + "/models") else 0
n_png = len(os.listdir(D + "/renders77")) if os.path.isdir(D + "/renders77") else 0
finished = os.path.exists(D + "/split_report.json")

prev = json.load(open(STATE)) if os.path.exists(STATE) else {}
cur = {"done": done, "n_models": n_models, "n_png": n_png, "finished": finished}

# ничего не изменилось — молчим. Исключение: переход в «готово» один раз.
if cur == prev and not (finished and not prev.get("finished")):
    raise SystemExit(0)

json.dump(cur, open(STATE, "w"))
print("⏳ Вильена: %d/%d — предмет %s\n"
      "FBX: %d | рендеры: %d\n"
      "Осталось ~%d мин" % (done, TOTAL, last_n, n_models, n_png,
                            max(0, TOTAL - done) * 80 // 60))
```

Проверять дешевле, чем кажется — обязательно прогоняй оба режима:

```bash
rm -f state.json && python3 progress_report.py   # должен напечатать
python3 progress_report.py                        # должен быть ПУСТ
```

Второй пустой вывод — доказательство, что спама не будет.

## Регистрация cron

```
schedule = "5m"      # каждые 5 минут
repeat   = 30        # потолок: не создавай вечную задачу, сними после конца
no_agent = True
script   = progress_report.py
deliver  = "origin"
```

`repeat` обязателен. Прогон закончится, а cron без потолка продолжит
стучаться до следующей сессии.

### ⚠️ `script` — куда реально ищет планировщик

Валидатор отклоняет абсолютный и домашний путь:

```
Error: Script path must be relative to ~/.hermes/scripts/.
Got absolute or home-relative path: '/tmp/vil/progress_batch.py'
```

…но текст ошибки **врёт**. Валидатор пропускает имя файла, а раннер на
выполнении ищет его в **`/opt/data/scripts/`** — то есть `$PWD/scripts/`, а не
в `~/.hermes/scripts/`. Скрипт, скопированный по букве ошибки, падает на
каждом тике с `status: script failed`, а лог показывает:

```
Script not found: /opt/data/scripts/dario_progress.py
```

Домашний каталог терминала — `/opt/data/home`, значит
`~/.hermes/scripts/` = `/opt/data/home/.hermes/scripts/` — это **не то**
место, откуда запускается скрипт.

**Клади в оба каталога** — дёшево, а расхождение невозможно пропустить:

```bash
mkdir -p /opt/data/scripts ~/.hermes/scripts
cp /tmp/vil/progress_report.py /opt/data/scripts/dario_progress.py
cp /tmp/vil/progress_report.py ~/.hermes/scripts/dario_progress.py
```

В поле `script` — **только имя файла**:

```python
cronjob(action="create", script="dario_progress.py", no_agent=True,
        schedule="*/5 * * * *", repeat=30, deliver="origin")
```

### ⚠️ Успешное создание ≠ рабочая задача

`cronjob(action="create")` отвечает `success: true` даже когда скрипт не
найдётся. Всегда проверяй фактический запуск:

```python
cronjob(action="run", job_id=JOB)          # принудительный тик
cronjob(action="list")                    # смотреть last_status
```

`last_status` должен стать `"ok"`. Если `"error"` — открой лог прогона:

```bash
find /opt/data/cron/output -name '*.md' -newermt '-30 minutes' | tail -1
```

Там поле `**Status:** script failed` и точная строка `Script not found:`.

### ⚠️ Проверь дубликаты ДО создания

Перед `action="create"` — всегда `action="list"`. В сессии уже была задача
`Дарио: прогресс панорамы` (каждые 4 минуты) с тем же скриптом; я создал
вторую (каждые 5 минут). Обе падали, но после починки заспамили бы
пользователя **двмя** сообщениями каждые 4–5 минут.

```python
cronjob(action="list")   # найти job с тем же script/schedule-назначением
cronjob(action="remove", job_id=ДУБЛЬ)
```

### ⚠️ Дубликаты наследуют поломку

Старая задача указывала на `dario_progress.py` **до** того, как я этот файл
создал — и падала на каждом тике с самой первой минуты. Молчание при этом
выглядит как «прогресс не меняется», а не как «задача сломана». Поэтому
проверять надо **все** задачи в списке, а не только ту, что создал сейчас.

## Оценка времени: мерить, а не обещать

Не называй ETA до измерения. Планируешь «35–70 минут» — это догадка, и она
оказалась вдвое оптимистичной (фактически ~40 сек/предмет при 128 spp
и 1024², то есть 2.1 часа на 211 предметов).

Меряй на коротком окне сразу после старта:

```bash
A=$(ls parts/*.fbx 2>/dev/null | wc -l); T0=$(date +%s)
sleep 120
B=$(ls parts/*.fbx 2>/dev/null | wc -l); DT=$(($(date +%s)-T0))
python3 -c "
a,b,dt,total=$A,$B,$DT,211
r=(b-a)/dt
print('%.3f предм/сек, осталось ~%.0f мин' % (r,(total-b)/r/60) if r>0 else 'нет данных')"
```

И включай это в сообщение пользователю: оценка на глаз не считается
обязательством, но обещание, не подкреплённое замером, почти всегда
оптимистично. Рендер на CPU — основной потребитель времени, разбиение FBX
почти мгновенно; при большом батче имеет смысл **сразу** предложить снизить
spp (`use_denoising` включён, разница на глаз минимальна).

## Скрипт-отчёт: не съедай состояние ручными прогонами

Скрипт пишет `STATE` и молчит, если состояние не изменилось. Ручной запуск
для отладки **потребляет** это изменение — и следующий тик cron уже промолчит,
хотя с точки зрения пользователя прогресс был. Для ручной проверки делай
`rm -f STATE` перед прогоном.

## Что писать в само сообщение

Только факты, которые человеку нужны для решения:

- `N/total (P%)` — сколько и доля
- номер **текущего** предмета
- счётчики файлов на диске (проверка, что процесс не встал)
- **оценка остатка** в минутах + на чём она основана («по 80 сек/предмет»)

Не писать: пути, полные команды, рассуждения о следующих шагах — это либо
не нужно, либо уже было в стартовом сообщении.

## Завершение

Когда батч дошёл и `split_report.json` создан, последний полезный тик —
**«готово, дальше проверка и загрузка»**, а не «77/77». Он снимает вопрос
«а не зависло ли», после чего cron нужно снять (`action=remove`).

## Смежное: как запустить длинный батч

Если `terminal(background=true)` с длинной командой блокируется по таймауту —
не повторяй её. Собери команду в runner-скрипт `.sh` и запусти **его**:

```bash
# runner.sh: blender ... > "$LOG" 2>&1; echo "EXIT=$?" >> "$LOG"
bash /tmp/vil/run_split77.sh
```

Лог пишется на диск, в контекст идёт только отфильтрованный хвост — это
правило №2 из `references/token_economy.md`, применённое к фоновым прогонам.
