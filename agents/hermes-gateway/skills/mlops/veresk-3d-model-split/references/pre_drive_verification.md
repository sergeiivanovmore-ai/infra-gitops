# Финализация: проверка, сохранение, манифест

Кейс Вильены, элементы 7 и 11: экспорт → рендер → Drive → **проверка**.
Здесь то, чего не было в пайплайне: чем доказывать, что вырезано и
загружено именно то, и куда всё положить, чтобы не потерять.

---

## 1. Структурная проверка экспортированного FBX

Рендер показывает, что видно. Он **не показывает** лишние объекты внутри
файла. Если при экспорте сцена не была изолирована или сработал `--select`
не по тому правилу, в FBX попадут чужие объекты — и это уедет на Drive.

Проверка = повторный импорт выгруженного FBX и сверка с ожиданием:

```bash
python3 .../scripts/verify_export_fbx.py --fbx parts/7.fbx \
    --expect-objects 11 --expect-x 13.618:14.918 --expect-z 0.804:1.554
```

Выводит `VERIFY_JSON {...}`: число объектов, вершины, полигоны, габариты по
осям и список объектов с их габаритами. Расхождение → экспорт неверен,
**не грузить на Drive**.

Реальный результат по Вильене:

| Файл | Объектов | Вершин | Полигонов | X | Z |
|------|----------|--------|-----------|---|---|
| `7.fbx` | 11 | 10 384 | 19 427 | 13.618–14.918 | 0.804–1.554 |
| `11.fbx` | 11 | 9 996 | 18 198 | 19.249–19.749 | 0.065–2.265 |

Число объектов совпало с прогнозом probe (11 и 11) — это и есть главная
проверка: **сколько показал probe, столько должно быть в экспорте**.

## 2. Проверка загрузки на Drive: обратное скачивание + md5

HTTP 200 на загрузке говорит только о том, что запрос принят. Файл мог
улететь битым, обрезанным или с лишним `\r\n` (см. `multipart_upload_fix.md`).

Единственная надёжная проверка — скачать обратно и сравнить:

```bash
python3 .../scripts/verify_drive_roundtrip.py --manifest upload_result.json
```

Для каждого файла: скачивает по id, сверяет размер и **md5** с локальным.
Выводит `ROUND_TRIP: ALL OK` или список расхождений.

```
7.fbx        drive=574412 local=574412  md5 23ef9e4a31  OK
11.fbx       drive=551964 local=551964  md5 0a33bcbfdd  OK
7_iso.png    drive=499020 local=499020  md5 13098ddc2b  OK
11_iso.png   drive=370972 local=370972  md5 d466e9acde  OK
```

> Надёжнее, чем «сверяться по id в логе»: id подтверждает создание записи,
> а не целостность содержимого.

## 3. Токен: обновить ДО загрузки, не по факту 401

`access_token` из `google_token.json` может быть просрочен (на Вильене —
`expiry` за сутки до работы). Если полагаться на retry по 401, первый же
запрос упадёт и при первом файле. **Вызови `refresh()` в начале скрипта**
и только потом загружай — тогда 401 не будет вовсе.

## 5. Где всё хранить — `/tmp` не переживает перезапуск

В начале сессии работа предыдущего прогона в `/tmp/vil_tr` была **стёрта**
целиком, остался только один PNG. Постоянные пути на хосте Hermes:

```
/opt/data/workspace/dsh_model_split/<Имя_файла>/
├── input/Вильена.fbx        исходник
├── parts/7.fbx  11.fbx      вырезанные предметы
├── renders/7_iso.png  11_iso.png
├── renders/panorama/         нумерованные кадры всей модели
├── items_index.json          нумерация 77 предметов с координатами
├── MANIFEST.json             размеры + md5 + ссылки Drive
└── scripts/                  отработавшие скрипты прогона
```

Кириллица в имени папки блокирует `workdir` терминала — заведи ASCII-симлинк
и работай через него (см. технические грабли в
`ordinal_numbering_and_nested_modules.md`):

```bash
ln -sfn "/opt/data/workspace/dsh_model_split/Вильена" /tmp/vil
readlink -f /tmp/vil     # /opt/data/workspace/dsh_model_split/Вильена
```

## 6. `items_index.json` — не пересчитывать нумерацию заново

Результат probe + слияния сохраняется один раз и переиспользуется в следующей
сессии. Без него каждое «ещё два элемента» означает новый импорт 79 МБ FBX и
пересчёт кластеров — и риск, что нумерация «поедет» от другой версии probe.

```json
{"model":"Вильена.fbx","axis":"X","count":77,
 "merged_from_modules":99,"artifacts_removed":22,
 "items":[{"n":7,"x0":13.62,"x1":14.92,"width":1.3,"height":0.75,
           "objects":11,"type":"высокий"}, ...]}
```

Следующий запрос пользователя («а теперь 12 и 19») читается отсюда за секунды.

## 7. Уборка: не оставляй рендеры неудачных догадок

После четырёх промахов в папке осталось 6 рендеров **не тех** предметов
(`item15.png`, `item_19.png`, `pano_13_25.png`, `strip_13_25.png`, …).
Они выглядят как валидные результаты и в следующей сессии собьют выбор.

Удали их и проверочные копии `dl_*` из round-trip, а рабочие скрипты
собери в `scripts/`. Оставь только то, что соответствует выбранным номерам.
