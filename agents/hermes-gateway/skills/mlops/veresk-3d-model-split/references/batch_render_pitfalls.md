# Пакетный рендер: ловушки, каждая даёт «успешный» прогон

Прогон `ALL_DONE items=42 assigned=1081 empty=0` **не означает**, что файлы
годные. На Лорэне Премиум так прошёл рендер, где часть предметов была пустыми
серыми кадрами, а в другие попадали соседние шкафы. Пользователь увидел это
только глазами.

Кейс: `Лорэна Премиум.fbx`, 1082 меша, 890 actions, 42 предмета.

---

## 1. Экспорт по выборке, а рендер по всей сцене

```python
bpy.ops.export_scene.fbx(filepath=..., use_selection=True, ...)   # ОК, только предмет
...
bpy.ops.render.render(write_still=True)                            # СНИМАЕТ ВСЮ СЦЕНУ
```

Рендер не знает про `use_selection` — в кадр попадает всё, что есть в сцене.
Результат: у предметов, рядом с которыми стояли тёмные соседние корпуса, в кадр
вылезали чёрные фасады. Побочный эффект тот же, что у п.2 — лишняя геометрия
и медленный кадр.

Признак: предмет выглядит «целым, но с чёрным мусором по краям». Проверяется
сравнением md5 рендера до и после удаления чужих объектов.

**Перед рендером удалить из сцены всё, что не входит в предмет.**

---

## 2. OOM на длинных прогонах: один процесс Blender на предмет

`EXIT=137` = SIGKILL по памяти. Лорэна: 1082 меша × 890 actions импортируются
заново на каждой итерации, память растёт монотонно — предмет 38 упёрся в 3.8 ГБ
при 7.9 ГБ доступных и был убит **на середине рендера**, оставив FBX без PNG.

```
предмет 1..37  — работает, 26–43 сек/шт, пик 3.8 ГБ
предмет 38     — SIGKILL, renders/38_iso.png отсутствует
```

Проверка: `free -m` + лог Blender (`Mem:NNNN Peak:NNNN` в последней строке
рендера). Убитый процесс не пишет `ALL_DONE`.

**Один предмет = один процесс Blender.** Даже с `clear_scene()` в начале цикла
память полностью не освобождается.

```bash
for n in $(seq 1 $N); do
    LOR_ONLY=$n timeout 600 blender --background --factory-startup \
        --python batch.py >> log.txt 2>&1
    echo "PROGRESS $n/$N exit=$?" >> progress.txt
done
```

Бонус: предмет = чистая сцена → очистка в середине цикла не нужна, каждый
запуск воспроизводим изолированно, прогон **возобновляем** — уже готовые
пропускаются по наличию файла.

## 3. EMPTY-родители: удалять нельзя, панели улетают

В FBX бывают панели с `location = (-283.9, 52.7, -8.0)` при **корректном**
`matrix_world` (даёт x≈25.5, как и должно быть). Их позиция вычисляется через
родительскую EMPTY-группу (`Group2132580747`, тип EMPTY).

Код «удалить всё, что не входит в предмет» сносил и родителя — дочерние панели
мгновенно теряли мировую трансформацию и уезжали на сотни единиц:

```
СЦЕНА МИРОВАЯ: x[-349.000..349.000] y[-242.699..242.700] z[-226.000..226.000]
ЦЕНТР=(0,0,0) РАЗМЕР=698.000      # камера улетела за 1000 единиц
```

При этом габариты самого предмета верны: `BBOX x[26.604..27.304]`.

**Правильно:**

```python
for o in list(bpy.data.objects):
    if o.type != 'MESH' or o.name in want:
        continue
    bpy.data.objects.remove(o, do_unlink=True)

# EMPTY/прочее — только скрыть: удаление ломает трансформации детей
for o in bpy.data.objects:
    if o.type != 'MESH' and o.name not in want:
        o.hide_render = True
        o.hide_viewport = True
```

**Диагностика «предмет пустой»:** напечатать мировой bbox сцены **после**
очистки. Если он в разы больше габаритов предмета — удалены родители, а не
«камера промахнулась». Эта одна проверка отличает баг п.3 от бага п.1.

Поражает не всё: у Лорэны предметы 13–42 (где `scale=0.001`, нормальная
иерархия) рендерились верно даже с багом. Пустыми выходили предметы 3–6, 12 —
те, где есть панели с «далёким» `location`.

## 4. Структурная проверка рендеров не доказывает, что они непустые

Ложные «успехи», которые прошли **все** автоматические проверки:
размер 987 КБ, сигнатура PNG корректная, `1024×1024`, `empty=0` — а кадр пустой.

Самодельный распакщик PNG с самописной реализацией фильтров
(Sub/Up/Average/Paeth) дал **ложное «пусто» на заведомо хорошем рендере №1**
и одинаковые «15–22 цвета» на всех файлах — включая пустые. Тест врал в обе стороны.

**Не пиши свой PNG-декодер.** Проверять рендеры `vision_analyze` по выборке:

- первый предмет (крайний левый)
- предмет с присоединённым осколком
- самый широкий кластер (2.0 м)
- предмет с аномально малой высотой по профилю
- последний предмет (крайний правый)

Достаточно 4–5 изображений на 42 предмета.

## 5. Аргументы Blender — только через переменные окружения

```
blender --background --python script.py -- input.fbx out.json
  -> FileNotFoundError: '--background'
  -> RuntimeError: Couldn't open file '--background'
```

Разделитель `--` с последующими путями приводит к тому, что флаги читаются как
имена файлов. Пути передавать через `os.environ["FBX_PATH"]`.

Отдельно: `bake_anim=False` / `bake_anim_use_all_actions=False` существуют
**только у экспорта** FBX. У импорта таких ключей нет:
`TypeError: keyword "bake_anim" unrecognized`. Именно эти флаги чинили
779-секундный экспорт на Дарио.

## 6. Длинный цикл — только в фоне

```bash
for n in $(seq 1 42); do blender ...; done     # foreground
  -> BLOCKED: Command timed out. Do NOT retry
```

Блокируется **до старта**: ни лога, ни файлов, ничего не удалено. Выглядит как
«завис», хотя не запускалось ни разу. Особенно опасно в связке с `rm -rf` в той
же команде.

**Порядок:** сначала `mkdir` + `mv` старых файлов в `renders_old_HHMM/`
(откат), потом запуск в фоне, потом отчёт о старте с фактами
(номер предмета, время, ошибки).

Прогресс писать в отдельный `progress.txt` построчно — по нему проверять
состояние, а не по статусу фонового процесса:

```
PROGRESS 37/42 exit=0 13:41:12
PROGRESS 38/42 exit=0 13:41:39
```

## Чек-лист перед тем, как считать прогон успешным

- [ ] `EXIT=0`, в логе есть `ALL_DONE`, `empty=0`
- [ ] количество FBX == количество PNG, нумерация 1..N без пропусков
- [ ] сумма объектов по всем предметам == исходному числу мешей
- [ ] нет файлов < 2 КБ
- [ ] все PNG: сигнатура + `1024×1024`
- [ ] **5 рендеров просмотрены глазами** (не «файл непустой»)
- [ ] в каждом кадре только свой предмет — без чужой геометрии по краям
- [ ] прогон возобновляем: каждый предмет отдельный процесс, есть `progress.txt`
