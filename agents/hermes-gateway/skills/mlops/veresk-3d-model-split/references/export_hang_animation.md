# Диагностика «зависшего» экспорта FBX: реальная причина — анимация

Разбор кейса Дарио (116 МБ, 2375 мешей, 211 предметов). Батч умер на предмете
№89, 88 предметов готово, потом 13 часов тишины.

## Симптом

`bpy.ops.export_scene.fbx()` не падает и не выдаёт ошибку — просто идёт
крайне медленно. Предмет 89: 176 объектов, из них **60 с анимацией**.

| Что | Время | Размер FBX |
|---|---|---|
| 40 объектов, как есть | **779 сек** | 7.4 МБ |
| 176 объектов, как есть | не завершился за 20+ мин | — |
| 176 объектов, `bake_anim=False` | **0.38 сек** | 2.8 МБ |
| 176 объектов, `animation_data_clear()` | 0.33 сек | 2.8 МБ |
| Предмет 89 целиком (FBX + рендер 1024²/64 spp) | **59 сек** | — |

## Причина

**FBX-экспортёр прогоняет ВСЕ экшены сцены на каждый экспортируемый объект.**
В модели было `len(bpy.data.actions) == 674`. Стоимость линейная по числу
экшенов × объектов с `animation_data`, поэтому предметы без анимации
(напр. №88, 64 объекта) экспортировались за 0.2 сек, а №89 — за десятки минут.

Анимация для статичного изометрического рендера **не нужна вообще**.

## Проверка (одна строка после импорта)

```python
print("actions=%d" % len(bpy.data.actions))
print("с анимацией: %d из %d" % (
    sum(1 for o in meshes if o.animation_data and o.animation_data.action),
    len(meshes)))
```

Если `actions` > 0 и часть объектов с `animation_data` — это оно.

## Фикс

```python
bpy.ops.export_scene.fbx(
    filepath=path, use_selection=True,
    bake_anim=False,
    bake_anim_use_all_actions=False,
    bake_anim_use_nla_strips=False,
    bake_anim_force_startend_keying=False,
)
```

Альтернатива — вычистить данные перед экспортом:

```python
for o in sel:
    if o.animation_data:
        o.animation_data_clear()
for a in list(bpy.data.actions):
    if a.users == 0:
        bpy.data.actions.remove(a)
```

Прописано в `batch_split_render.py`, `split_selected.py`, `analyze_and_split.py`.

## 🚨 Ложные следы, на которые ушла большая часть времени

Ни одна из гипотез ниже не была причиной. Проверял их по очереди:

| Гипотеза | Что показала проверка | Вывод |
|---|---|---|
| **UV-слои** | «116 UV-слоёв» — это 116 **объектов** с одним слоем каждый, а не 116 слоёв на объекте | считать `len(o.data.uv_layers)` **на объекте**, а не сумму по модели |
| **Отрицательный масштаб** | `scale=[-1,-1,-1]`, `det=-1e-9` — таких объектов **285**, и все прочие предметы экспортировались за 0.2 сек. `transform_apply` исправил det → +1e-9, экспорт остался медленным | не причина |
| **Матрица вырождена** | `det=1e-09` у **всех 2375** объектов — это глобальный масштаб импорта FBX (единицы), а не аномалия | не причина |
| **Число объектов** | 20 объектов вместе — 0.08 сек; те же объекты поштучно — 0.04 сек; 40 вместе — 779 сек | не количество, а **сочетание** (анимация) |
| **OOM** | `dmesg` пуст, доступно 4+ ГБ из 7.9 ГБ | не причина |

**Порядок проверки, который сработал:** сначала `len(bpy.data.actions)` и
`animation_data`, потом всё остальное. Анимация — самая частая и самая
неочевидная причина.

## Метод локализации: поштучный экспорт

Когда непонятно, объект это или группа, экспортируй объекты **по одному** с
замером — виновник виден как строка, на которой время уходит вверх:

```python
for k in range(lo, hi):
    bpy.ops.object.select_all(action='DESELECT')
    sel[k].select_set(True)
    bpy.context.view_layer.objects.active = sel[k]
    t = time.time()
    bpy.ops.export_scene.fbx(filepath=p, use_selection=True)
    dt = time.time() - t
    print("%3d %7.2f %s" % (k, dt, sel[k].name), flush=True)   # flush обязателен
```

`flush=True` обязателен: без него при `timeout` и убийстве процесса теряется
весь буфер и лог выглядит пустым — создаётся впечатление «завис с самого
начала», хотя видно только последний сброшенный буфер.

## 🚨 Проверяй на ТОЙ ЖЕ модели, где было зависание

Главная ошибка кейса: экспорт стабильно шёл 0.7–2 сек на **Penaly**
(110 мешей), и я заключил «зависания не существует». Зависание было на
**Dario** (2375 мешей, 674 экшена) — другая модель в той же сессии.

Перед выводом «зависания нет»:

```python
print("MESH=%d" % len(meshes))   # должно совпасть с объектом-источником задачи
```

Число объектов в диагностике **обязано** совпасть с моделью, на которой
зависало. Иначе вывод неверен по построению.

## Воспроизводимый пробник

`scripts/diag_export_hang.py` — один импорт, замеры по конфигурациям экспорта
и поштучный прогон. Запуск:

```bash
blender --background --factory-startup --python scripts/diag_export_hang.py -- \
    '{"fbx": "<model.fbx>", "index": "<items_index.json>", "item": "89", "lo": 20, "hi": 50}'
```

Печатает `>>> НАЧАЛ` перед каждым экспортом, поэтому по логу сразу видно,
на каком шаге встал процесс.
