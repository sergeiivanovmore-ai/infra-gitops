# Изоляция сцены при рендере: три ловушки, найденные на Лорене Премиум

Модель: `Лорэна Премиум.fbx`, 1082 mesh, 490k полигонов, 890 actions,
габариты 61.1 × 1.7 × 2.6. Результат: 42 предмета, 1081 объект.

Все три ловушки выглядят как «скрипт отработал успешно».

---

## 1. Экспорт по выборке, рендер всей сцены

`export_scene.fbx(use_selection=True)` выгружает только выделенное.
`bpy.ops.render.render()` снимает **всю, что есть в сцене**.

Симптом: в кадре предмета видны чёрные фасады и куски соседних шкафов.
Проверка размеров файлов при этом проходит — FBX-то корректные.

```python
# только чужие MESH
for o in list(bpy.data.objects):
    if o.type != 'MESH' or o.name in want:
        continue
    bpy.data.objects.remove(o, do_unlink=True)
```

Побочный эффект: пока в сцене 1082 объекта, память растёт → см. ловушку 3.

## 2. Удаление EMPTY-родителей рвёт трансформации детей

**Самая дорогая ошибка.**

В файле 47 объектов имеют:

```
loc=(-283.91, 52.70, -8.00)  scale=(1.0, 1.0, 1.0)  dim_local=(0.485, 0.436, 0.016)
```

При этом `matrix_world` у них **правильный** (`x[25.555..25.571]`) — это дети
групп `Group2132580747` (тип EMPTY, 47 штук), которые и задают смещение.

Если удалить родителя вместе с «всем вне предмета», наследование обрывается:
дочерние панели оказываются в мировых координатах ±349 по всем осям.

```python
# ПРАВИЛЬНО: EMPTY скрывать, но НЕ удалять
for o in bpy.data.objects:
    if o.type != 'MESH' and o.name not in want:
        o.hide_render = True
        o.hide_viewport = True
```

### Диагностика

Напечатать мировые габариты сцены **после** очистки и сравнить с габаритом
предмета:

```
СЦЕНА МИРОВАЯ: x[-349.000..349.000] y[-242.699..242.700] z[-226.000..226.000]
ЦЕНТР=(-0.000,0.000,-0.000) РАЗМЕР=698.000
КАМЕРА БЫЛА БЫ: (1055.376,-1348.536,850.164) d=1465.800
```

Габарит предмета при этом `x[25.555..26.253]` — сцена в ~700 раз шире.
Это однозначный признак сорванных родителей.

Быстрые флаги у членов группы:

```python
tiny = max(abs(s) for s in o.scale) < 0.01
far  = max(abs(v) for v in o.location) > 50
```

Оба флага встречаются и у нормальных объектов (см. `scale=0.001` у части
панелей), поэтому сами по себе они не приговор — приговор, когда **рендер пуст**.

## 3. OOM на длинных батчах

Память росла с каждой итерацией повторного импорта FBX: пик 3.8 ГБ,
`EXIT=137` (SIGKILL от OOM) на 38-м предмете из 42.

**Один предмет = один процесс Blender.** См. `scripts/run_batch_isolated.sh`.

Побочная польза: после починки ловушки 1 время на предмет упало с 34 сек
до 8.3 — рендерилось вчетверо больше геометрии, чем нужно.

### Детектор по размеру файла

```python
import os
from collections import Counter
d = 'renders'
sz = {int(f.split('_')[0]): os.path.getsize(os.path.join(d, f))
      for f in os.listdir(d) if f.endswith('_iso.png')}
for size, n in Counter(sz.values()).most_common(3):
    if n > 1:
        print('одинаковый размер %d у %d файлов: %s'
              % (size, n, sorted(k for k, v in sz.items() if v == size)))
```

### Правило

**Перед загрузкой на Drive всегда открывай 3–4 рендера через
`vision_analyze`** — лучше те, что вызывают подозрение (пустые, узкие,
с осколками). Никакой автоматический тест это не заменяет.

Собственный декодер PNG на голом `zlib` (unfilter строк) дал ложный
результат на всех 42 файлах — не использовать как индикатор.

## Запуск Blender из харнесса

**`--` как разделитель аргументов ломает их:**

```
FileNotFoundError: [Errno 2] No such file or directory: '--background'
```

Флаги читаются как имена файлов. Передавать пути через **переменные
окружения** (`LOR_FBX`, `LOR_OUT`), а не через `sys.argv`.

**EEVEE не работает в headless** — нужен GPU и `libEGL.so.1`:

```
Couldn't open libEGL.so.1: cannot open shared object file
```

Рабочий движок — **Cycles CPU** (`samples=64`, `res=1024`, ~20 сек/предмет).

**Длинные циклы — только в фоне.** `for n in $(seq 1 42)` (~7 мин) в
foreground блокируется харнессом по таймауту **до старта**: ни лога, ни
процесса. Выглядит как «завис», но ничего не запускалось. Обёртка в `.sh` +
`background=true`.

## Разбиение плотного ряда: интервальное объединение

Крупнейший зазор 0.72 при длине 61.1 = 1.2% → разбиение по зазорам
неприменимо. Сработало объединение интервалов:

```python
iv = sorted((x0, x1, name) for ...)
merged = []
for a, b, nm in iv:
    if merged and a <= merged[-1][1] + 1e-9:
        merged[-1][1] = max(merged[-1][1], b)
    else:
        merged.append([a, b, [nm]])
```

43 блока при 42 зазорах — совпадение с числом видимых корпусов.

Осколок: `n_obj <= 2 and w < 0.06` → ближайшему соседу по X (зазор 0.001).

**Широкий кластер ≠ два предмета.** Блоки 2.0 — единые шкафы на 4 двери
(слитный цоколь, общие фасады). Резать по ширине нельзя, проверять изометрией.
