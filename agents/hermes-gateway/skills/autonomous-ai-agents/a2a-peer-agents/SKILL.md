# Делегирование пировым A2A-агентам

«Попроси агента X», «передай агенту X» — это НАСТРОЕННЫЙ ПИР (другой контейнер, свой
профиль, свой доступ к Docker-хосту), а не субагент и не `delegate_task`.
Инструменты: `a2a_list`, `a2a_call`, `a2a_history`, `a2a_discover`, `a2a_orchestrate`.
Роль оркестратора: точная передача задачи, дробление, проверка, сжатый отчёт — НЕ
выполнение работы пира за него и не выдумывание результата.

## When to Use

- Пользователь говорит «попроси агента <имя>…» / «передай агенту <имя>…», где имя —
  настроенный A2A-пир (системный админ, мониторинг, почта).
- Нужны данные или действия, доступные ТОЛЬКО с той стороны: Docker-хост, состояние
  сервисов, правка файлов в его файловой системе.
- Пир вернул таймаут/пустой ответ и нужно решить: дробить, пинговать статус или делать
  артефакт локально.

## Порядок действий

### 1. Сначала `a2a_list` — никогда не угадывай пира
Список даёт имена, URL, capabilities и существующие `context_id`.
Если пользователь называет пира, которого нет (например «ops»), не выдумывай его и не
молчи: перечисли, кто реально настроен, и дальше работай с тем, чьи capabilities
покрывают задачу (например `sysadmin` — sysadmin/server_management/monitoring).

### 2. Новый топик — новый контекст, продолжение — `context_id`
Продолжение той же темы отправляй с `context_id` из предыдущего ответа, иначе пир
теряет состояние (файлы, ранее собранный снимок). Не плоди параллельные контексты для
одной задачи.

### 3. Один вызов — один проверяемый результат
Составные задания («обнови файл + отрендери PNG + верни полный текст») пир обрывает по
таймауту. Режь на шаги с одним артефактом на вызов; сборку/рендер всего, что можно
сделать локально, оставляй себе.

### 4. После таймаута — СТАТУС-ПИНГ, а не повтор задачи
Ответ `[agent did not reply in time]` не означает «не сделал»: пир мог уже выполнить
часть. Повтор всей задачи рискует продублировать побочные эффекты и снова упрётся в
таймаут.
Вместо этого задай минимальный вопрос с явным запретом что-либо ещё делать:
«ответь одной строкой: файл обновлён? назови версию в шапке и есть ли рядом .bak.
Больше ничего не делай» — такое сообщение доходит и возвращает всё состояние.
Повторять длинный запрос дважды подряд бесполезно — это сигнал дробить.

### 5. Пир не отдаёт артефакты — возьми у него текст
У пира нет нужных бинарей (например `mmdc`), а его попытка поставить их через `npx`
встаёт на подтверждении. Проси у него ДАННЫЕ (путь к `.mmd`, готовый mermaid-код,
путь+размер файла), а PNG/сборку делай локально — рецепт:
`references/mermaid-render-to-png.md`.

### 6. Проверяй побочные эффекты сам
Самоотчёт пира («обновил, версия 1.1», «удалил», «загрузил») — не доказательство.
Минимально дешёвая проверка: версия/шапка файла, наличие `.bak`, размер, сигнатура и
размеры бинарника. Если чего-то проверить нельзя (нет доступа, нет vision) — так и
скажи, не выдавай артефакт за проверенный.

**Когда у пира нет хостового shell, а действие он сделал у себя** (docker rm/rmi,
правка файлов в его ФС) — независимый путь проверки: прогнать read-only команду
через СВОЙ DSH-агент (`mcp__dsh_carrot__agent_run`), это другой канал к тому же
Docker-демону/хосту. Формулируй задачу как «выполни РОВНО N read-only запросов и верни
сырой вывод, больше ничего не делай, не удаляй/не меняй» и проси `detail=normal`,
чтобы пришли и `toolResults` (сырой stdout), а не только сводка. Отчитывайся в формате
«подтверждено моим независимым замером» vs «подтверждено только самоотчётом пира».

**Деструктивные операции по заказу пользователя** (удаление контейнера/образа, закрытие
портов) — передавай пиру с условием и доказательствами: сначала `docker inspect`
(State.Status/Running/ExitCode, RestartPolicy.Name, Privileged, Mounts, SecurityOpt),
явное условие «удалять только если действительно не Running», запрет `-f`, затем
post-check (`ps -a`, `images`) и подтверждение, что остальные сервисы целы.
Автозапуск на уровне Docker проверяется через `RestartPolicy.Name=no`; хостовый
systemd/compose-автозапуск из контейнера принципиально не проверяется — пиши
«не проверено», а не «нет автозапуска».

## Отчёт пользователю

- Сначала результат, потом что именно проверено, потом что осталось. Короткие буллеты,
  без воды и без заголовков «Отлично, задача выполнена».
- Не пересылай сырой транскрипт пира — сжимай до таблицы/буллетов, но сохраняй имена
  контейнеров, порты, версии, пути и все предупреждения пира.
- Каждый ответ пира несёт `context_id` — при пересылке полезно назвать его, чтобы
  следующая сессия могла продолжить диалог (`a2a_history`).
- Предупреждения пира о «не проверено» (нет хостового shell, не смотрел firewall/UDP)
  переноси в отчёт как есть — это не шум, а граница доказанного.

## Подводные камни

- **Не отбрасывай высокий CPU контейнера как «артефакт».** Замер `docker stats` ~100% —
  обычно РЕАЛЬНАЯ устойчивая нагрузка (≈ одно ядро), а не ошибка усреднения `%CPU`:
  сличай `usage_usec` из `/sys/fs/cgroup/cpu.stat` дважды с интервалом 10 с (изнутри
  контейнера) — дельта ~0.9–1.0 ядра подтверждает. Диагноз ставь по СМЕНЕ PID сервиса,
  а не по среднему: если один и тот же `comm` появляется с новым PID каждые 5–10 с,
  это crash-restart loop под s6-supervise (в контейнерах Hermes — сервис `dashboard`).
  Кратковременные PID'ы с 99% в `ps` — не «запуск CLI», а именно перезапускаемый сервис.
  Причина видна в `docker logs <контейнер>` (stdout), а не в файлах `logs/*.log`:
  например `Refusing to bind dashboard to 0.0.0.0 — no auth providers are registered`.
- **Не переноси диагноз пира без проверки.** Пир назвал виновником `hermes gateway run`
  (у него низкое среднее, ~1.6% за всё время жизни) — реальный виновник был другой
  сервис того же контейнера. Свои замеры изнутри контейнера — дешёвый способ уточнить.
- **Нет хостового shell у пира** — `systemctl`, `ss`, чтение хостовых процессов из его
  DSH недоступны. «Недоступно» — честный ответ; фиксируй как «не проверено», не
  додумывай состояние хоста.
- **Внутренние противоречия документа-эталона** (одно и то же значение в разных
  разделах) выноси отдельной строкой как расхождение, а не выбирай молча одно из двух —
  факт из `docker inspect` решает.
- **Деструктивные операции у пира требуют подтверждения** — предложение «удалить
  остановленный контейнер» переноси пользователю, не подтверждай от его имени.
- **Рестарт гейтвея** рвёт вызов: после восстановления сессии не переигрывай старые
  вызовы, а отчитайся о восстановлении и назови, что осталось незавершённым.
