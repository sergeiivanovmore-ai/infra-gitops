# agents/ — настройки Hermes-агентов

Здесь лежит всё, что описывает агентов декларативно. Деплой применяет эти файлы
на хост; руками живые конфиги править не нужно и нельзя — следующая сходимость
затрёт правку.

## Что где лежит

- `agents/<агент>/models.yaml` — модель и провайдер. Применяет
  `scripts/apply-agent-models.sh`. **Обязательный файл**: без него для агента не
  применяются и настройки ниже.
- `agents/<агент>/settings/<группа>.yaml` — переопределение групп `config.yaml`,
  включая `mcp_servers`. Применяет `scripts/apply-agent-settings.sh`. Каталог
  обходится только при наличии `models.yaml` рядом. Имя файла = имя группы,
  белого списка нет.
- `agents/<агент>/skills/` — скиллы, которые деплой раздаёт агенту (`rsync` из
  `scripts/deploy-infra.sh`).
- `agents/<агент>/state/` — **здесь не лежит**. Состояние (самодельные скиллы и
  память) пишется в приватный репозиторий `hermes-agent-state`, скриптом
  `scripts/sync-agent-state.sh`.

## Два репозитория

- **infra-gitops** (этот, публичный) — скрипты, compose, approvals, models,
  settings. Всё, что не содержит секретов.
- **hermes-agent-state** (приватный) — память и навыки, накопленные агентами в
  рантайме. Публичным быть не должен: там содержимое памяти.

Секреты не кладём ни в один из них. Они живут в `.env` рядом с агентом, либо
закрепляются через managed scope Hermes (`/etc/hermes/.env`).

## Что синкается в состояние

- **Память (`memories/`) — да.** Синкается в приватный `hermes-agent-state`
  скриптом `scripts/sync-agent-state.sh`: автокоммит в ветку `state/auto`,
  раз в неделю — консолидирующий PR в `main`.
- **Скиллы (`skills/`) — пока нет.** В контейнере около 110 скиллов приезжает из
  образа контейнера; зеркалировать каталог целиком — это 2175 файлов на пять
  агентов плюс дублирование одних и тех же встроенных скиллов по каждому агенту.
  Нужен механизм различения встроенных и кастомных скиллов — **issue #84**. До его
  реализации скиллы в состояние не попадают, и правки агента во встроенных
  скиллах живут только внутри контейнера.

## Как подключить нового агента

1. Создать `agents/<имя>/models.yaml`:

   ```yaml
   kind: hermes
   config: /opt/docker/<имя>/data/config.yaml
   restart: <имя>
   model_provider: openrouter
   model_default: <провайдер/модель>
   ```

   Ключ `config:` не только указывает целевой конфиг — из него выводится каталог
   данных агента, поэтому других таблиц соответствий нигде нет.

2. Опционально: `agents/<имя>/settings/<группа>.yaml` — для групп `config.yaml`.
3. Опционально: `agents/<имя>/skills/` — скиллы для раздачи агенту.
4. Добавить один блок в `scripts/deploy-infra.sh`, по образцу соседних:

   ```bash
   if agent_recreate_ok <имя>; then
     ... копирование файлов и docker compose up -d ...
   fi
   ```

5. Состояние подхватится само. `scripts/sync-agent-state.sh` обходит **все**
   `agents/*/models.yaml`, а каталог данных агента берёт из ключа `config:`
   того же файла. Правок в скрипте для нового агента не требуется.

Единственная ручная часть — шаг 4. Всё остальное работает автообнаружением.

## Чего здесь делать нельзя

- Править `config.yaml` агента на хосте руками — только файлами этого репозитория.
- Класть токены и ключи.
- Заводить новую механику под конкретное имя агента: список агентов везде
  берётся из `agents/*/models.yaml`, а каталог данных — из `config:`.

## Порты

Все агенты слушают только на 127.0.0.1, наружу доступ идёт через прокси.
Хостовые порты различаются, чтобы агенты не конфликтовали между собой.

| Агент | API | Dashboard |
| --- | --- | --- |
| hermes-gateway | 8641 | 9118 |
| hermes-work | 8642 | 9119 |
| hermes-orchestrator | 8643 | 9120 |
| hermes-sysadmin | 8653 | 9121 |

Внутри контейнера порты всегда одни и те же: 8642 (API) и 9119 (dashboard).
Меняется только хостовый порт слева.

## Применение изменений compose

Изменения запуска контейнера применяются только пересозданием:

    cd /opt/docker/<агент>
    docker compose down && docker compose up -d

`docker start` для этого не годится. Он не применяет ни порты, ни сети, ни
переменные: контейнер поднимается с тем, что было записано в него при создании.
Если за время простоя пересоздавали сеть, старый контейнер остаётся без
endpoint и теряет связь с остальными сервисами, хотя формально он «запущен».

Именно так произошёл инцидент с hermes-gateway: контейнер простоял две недели,
за это время mcp-network пересоздавали при добавлении orchestrator и work в
GitOps, и обычный `docker start` вернул его в сеть без endpoint.
